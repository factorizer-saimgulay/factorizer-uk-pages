ULID primary keys

Decision record for the rule that Cluster ERP primary keys are ULIDs stored as UUID, with standard audit columns and business keys from core_sequences.

Contents

  • Context
  • Decision
  • Consequences
  • Where the code enforces it
  • Related pages

Status: Accepted, stated in the project's written engineering rules. This record covers three linked rules: primary keys are ULIDs stored in a UUID column, every record carries the same audit columns, and human-readable business keys come from core_sequences. The base class is explained on base model and ids.

Context¶

The project's written engineering rules ask for keys that sort by creation time and carry a time prefix, and for business keys made of a prefix and a counter, some reset yearly. The docstring of new_ulid states the property the code relies on: the value is time-sortable, globally unique, and compatible with PostgreSQL's native uuid type (src/cluster_erp/core/ulid.py:8-14). Further rationale is not determined from code.

Decision¶

  • BaseModel.id is a UUID primary key whose default is new_ulid (src/cluster_erp/core/models.py:20-24).
  • BaseModel adds tenant_id, created_at, created_by, updated_at, updated_by, deleted_at, deleted_by, deactivation_reason, deactivation_note, and version (src/cluster_erp/core/models.py:25-78).
  • Business keys come from next_code, which reads and advances one core_sequences row per entity type (src/cluster_erp/core/sequence.py:112-120, src/cluster_erp/core/sequence.py:154-171).

The flowchart shows how a new record gets its keys.

In prose: the change-history listener assigns the ULID before the insert, so the history row of a new record carries its id (src/cluster_erp/core/change_history.py:273-281). A service that needs a business key calls next_code. For yearly entities the code contains the year and a five-digit counter; for the others a six-digit counter (src/cluster_erp/core/sequence.py:86-109, src/cluster_erp/core/sequence.py:168-171). The counter restarts when the calendar year changes (src/cluster_erp/core/sequence.py:194-197).

Consequences¶

  • Ids are created in Python, not in the database. The listener materialises them early so the history is complete (src/cluster_erp/core/change_history.py:273-278).
  • version starts at 1 on every row (src/cluster_erp/core/models.py:73-78).
  • 19 entity types reset their counter each year, listed in YEARLY_ENTITIES (src/cluster_erp/core/sequence.py:88-108, counted from the set). All other entity types count continuously, for example parties with prefix PTY (src/cluster_erp/core/sequence.py:15).
  • Missing sequence rows are seeded at start-up by seed_sequences (src/cluster_erp/core/sequence.py:123-151).

Where the code enforces it¶

Mechanism What it checks Source
BaseModel Every business model inherits the key and audit columns src/cluster_erp/core/models.py:17-78
_ensure_pk A new object has its id before the history row is made src/cluster_erp/core/change_history.py:273-281
_advance A missing sequence row raises an error instead of inventing a key src/cluster_erp/core/sequence.py:182-199

Not determined from code: a test that every table uses a ULID key. None was found in tests/ (searched for new_ulid and ulid).

Warning

Discrepancy. The project's written engineering rules make every primary key a ULID stored as UUID. The control-plane classes Operator and OperatorAction default their key to uuid.uuid4 (src/cluster_erp/core/tenancy.py:138, src/cluster_erp/core/tenancy.py:163). ControlRetentionRun, RetentionRun, and one analytics table use an auto-incrementing BigInteger key (src/cluster_erp/core/tenancy.py:194, src/cluster_erp/modules/records/retention/models.py:44, src/cluster_erp/modules/analytics/models.py:123). This page documents the code.
