Material requirements planning

How the MRP run in procurement collects demand and supply, explodes BOMs, nets, sizes lots, raises exceptions, and turns proposals into requests or orders.

  • Limits and open points
  • Terms introduced
  • Related pages

Material requirements planning (MRP) lives in src/cluster_erp/modules/procurement/mrp/. A planning run (MrpRun) compares demand with stock and open supply for each product, explodes bills of materials, and stores one result row (MrpRunItem) per product with a proposal and an exception message. This page explains how a run works and how its results are used. Field lists are on the procurement module page and in the source; the BOM explosion is described on the BOM module.

In short¶

  • A run has seven phases: init, demand, supply, low-level coding, netting, exceptions, and result assembly (src/cluster_erp/modules/procurement/mrp/engine.py:1-19).
  • Only one run can be running at a time; a database advisory lock guards the check (src/cluster_erp/modules/procurement/mrp/services.py:157-176).
  • All data from other modules arrives through EventBus queries such as GetOpenSalesOrderDemand, GetBulkStockLevels, and GetBomExplosion (src/cluster_erp/modules/procurement/mrp/engine.py:871, src/cluster_erp/modules/procurement/mrp/engine.py:1325, src/cluster_erp/modules/procurement/mrp/engine.py:1720).
  • Stock and production events mark the run stale and flag products in a planning file for the next net-change run (src/cluster_erp/modules/procurement/module.py:863-1003).
  • Run items become purchase requests or production orders by explicit actions (src/cluster_erp/modules/procurement/mrp/services.py:331, src/cluster_erp/modules/procurement/mrp/routes.py:359-375).

How it works¶

A run starts with POST /mrp/runs (synchronous) or POST /mrp/runs/background (returns at once with status running) and the parameters of MrpRunCreate (src/cluster_erp/modules/procurement/mrp/routes.py:105-121, src/cluster_erp/modules/procurement/mrp/schemas.py:28-70). The diagram shows the phases.

In prose:

  1. Init. The engine creates the run with status running and snapshots the parameters (src/cluster_erp/modules/procurement/mrp/engine.py:769-823). With delete_and_recreate, the items of the previous completed run are bulk-deleted and one summary change-history row is written; with normal, the BOM cache of the previous run is preloaded (src/cluster_erp/modules/procurement/mrp/engine.py:555-562, src/cluster_erp/modules/procurement/mrp/engine.py:697-767).
  2. Demand. Demand comes from open sales orders, open production order components, planned independent requirements (PIRs), safety stock deficits, and reorder points. A run with scope project first derives its product list from the project's demand (src/cluster_erp/modules/procurement/mrp/engine.py:824-977, src/cluster_erp/modules/procurement/mrp/engine.py:1059).
  3. Supply. Stock levels, open purchase orders, production supply, production versions, vendors, and substitutes are read in bulk (src/cluster_erp/modules/procurement/mrp/engine.py:1311-1626).
  4. Low-level coding. Each manufactured product gets the active BOM version, and the BOM is exploded to assign low-level codes; the scope grows with BOM children (src/cluster_erp/modules/procurement/mrp/engine.py:1627-1920).
  5. Netting. Requirements are netted per time bucket with dependent demand from BOMs, phantoms, substitution, lot sizing, scrap, lead-time offset, and vendor selection (src/cluster_erp/modules/procurement/mrp/engine.py:1921-2599). Lot sizing uses the run's rule, or the setting for the product's ABC class (src/cluster_erp/modules/procurement/mrp/engine.py:3037-3093). Lead-time dates use the vendor's working calendar first, then the company group calendar, through GetOwnerWorkingDays (src/cluster_erp/modules/procurement/mrp/engine.py:3247-3287).
  6. Exceptions. Each product gets at most one main exception: new_order, reschedule_in, reschedule_out, cancel, decrease_qty, increase_qty, or expedite. Damping margins come from settings (src/cluster_erp/modules/procurement/mrp/engine.py:3405-3600, src/cluster_erp/modules/procurement/mrp/engine.py:2817).
  7. Assembly. Items are stored in chunks, run totals are updated, the status becomes completed or simulation, and MrpRunCompleted and CriticalMaterialAlert are emitted (src/cluster_erp/modules/procurement/mrp/engine.py:3880-4118).

If a phase fails, the run gets status failed with the error message and duration (src/cluster_erp/modules/procurement/mrp/engine.py:594-607). When output_type is purchase_requisition, a completed run creates purchase requests at once (src/cluster_erp/modules/procurement/mrp/services.py:188-189).

Why it is built this way¶

The module docstring of the engine names the seven-phase algorithm and the netting method (src/cluster_erp/modules/procurement/mrp/engine.py:1-19). Code comments give two reasons: bulk deletion of previous run items avoids per-row history for regenerable rows (src/cluster_erp/modules/procurement/mrp/engine.py:718-721), and a net-change baseline is taken only from a run that carries a plan (src/cluster_erp/modules/procurement/mrp/engine.py:2835-2842). Other rationale is not stated in code or in the project's written engineering rules.

Rules and boundaries¶

  • run_type is regenerative or net_change; planning_mode is normal, re_explode_bom, or delete_and_recreate; scheduling_method is backward, forward, lead_time, or basic_date; lot_size_rule is default, lot_for_lot, fixed_order, period_order, or eoq; scope is all, abc_class, product, product_group, warehouse, project, or mps_items (src/cluster_erp/modules/procurement/mrp/schemas.py:28-67).
  • A simulation run does not touch previous items (src/cluster_erp/modules/procurement/mrp/engine.py:556).
  • A purchase request can be made only from a completed run (src/cluster_erp/modules/procurement/mrp/services.py:331-345).
  • Converting a planned order to a production order outside the opening period needs force; the conversion is the query CreateProductionOrderFromPlanned (src/cluster_erp/modules/procurement/mrp/routes.py:359-447).
  • POST /mrp/runs/{run_id}/materialize reruns a simulation as a real run with the same parameters (src/cluster_erp/modules/procurement/mrp/routes.py:545-560).
  • Deleting a run sets deleted_at on the run and its items; a running run cannot be deleted (src/cluster_erp/modules/procurement/mrp/services.py:1217-1246).
  • Run items can be firmed and unfirmed; firmed items are loaded by later runs (src/cluster_erp/modules/procurement/mrp/services.py:1284-1368, src/cluster_erp/modules/procurement/mrp/engine.py:2966).
  • The run stores quantities and costs as Numeric, and durations are rounded with ROUND_HALF_EVEN (src/cluster_erp/modules/procurement/mrp/engine.py:599-602).

Limits and open points¶

Warning

Discrepancy. The project's written engineering rules make the product, model, and version breakdown mandatory for stock and movement keys and forbid a silent fallback. The MRP run plans per product_id; when it stores a run item it takes the product's default model and version from GetBulkProductDefaultBreakdowns, and fails the run if a product has none (src/cluster_erp/modules/procurement/mrp/engine.py:3893-3940). Creating a PIR without model and version also takes the default breakdown (src/cluster_erp/modules/procurement/mrp/routes.py:782-793). This page documents the code.
