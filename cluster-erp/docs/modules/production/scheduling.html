Production scheduling

How the production scheduling board reads work orders, resolves each work center's working calendar, detects conflicts and capacity, and moves or auto-schedules work orders.

Contents

  • In short
  • How it works
  • Why it is built this way
  • Rules and boundaries
  • Interaction with other parts
  • Limits and open points
  • Terms introduced
  • Related pages

The scheduling board lives in src/cluster_erp/modules/production/scheduling/. It shows work orders as bars on work-center rows over time, computed against each work center's effective working calendar, and it moves, resizes, or auto-schedules them. The web app (scheduling_board) and the desktop (scheduling_board.py) draw the same data. Work order fields are on work orders; calendar math is on working time.

In short¶

  • GET /api/v1/production/scheduling/board returns one read model: work centers with shifts and holidays, scheduled bars, the unscheduled pool, conflicts, capacity cells, and dependencies (src/cluster_erp/modules/production/scheduling/routes.py:41-86, src/cluster_erp/modules/production/scheduling/services.py:170-313).
  • Each work center's calendar is resolved through the owner chain work center, then the party of its organisation or of the headquarters, then the company group calendar (src/cluster_erp/modules/production/scheduling/services.py:72-94).
  • A work order's end is always derived from its duration laid over working hours; a caller cannot set it (src/cluster_erp/modules/production/scheduling/services.py:314-388).
  • The time math comes from the shared engine core.working_time, re-exported by scheduling/calendar.py (src/cluster_erp/modules/production/scheduling/calendar.py:1-30).

How it works¶

The diagram shows the data path of a board read.

In prose:

  1. The route takes date_from, date_to, and optional work center, production order, project, and scope filters; it needs work_order.read (src/cluster_erp/modules/production/scheduling/routes.py:41-86).
  2. The service loads the work centers and resolves each one's effective calendar with one GetEffectiveWorkingCalendars query over the owner chains (src/cluster_erp/modules/production/scheduling/services.py:891-946).
  3. Holidays and exceptions per date come from GetCalendarWindows; the effective time zone comes from the calendar, the organisation, or GetCompanyDefaultTimezone (src/cluster_erp/modules/production/scheduling/services.py:780-874, src/cluster_erp/modules/production/scheduling/services.py:982-1016).
  4. Work orders in the window become bars; pending ones without a schedule form the unscheduled pool (src/cluster_erp/modules/production/scheduling/services.py:1038-1204).
  5. Overlaps are flagged per work center, allowing up to capacity_units parallel bars; capacity cells and over-capacity days are computed; finish-to-start dependencies and predecessor violations are added (src/cluster_erp/modules/production/scheduling/services.py:1205-1384).

Writes:

  • PUT /scheduling/work-orders/{work_order_id}/schedule moves, resizes, reassigns, or unschedules one pending work order. It checks the record version, snaps an explicit start forward to the next working instant, and derives the end (src/cluster_erp/modules/production/scheduling/routes.py:87-109, src/cluster_erp/modules/production/scheduling/services.py:314-388).
  • POST /scheduling/work-orders/{work_order_id}/auto-schedule snaps a work order to the nearest valid free slot after its predecessors; no slot gives a 422 (src/cluster_erp/modules/production/scheduling/routes.py:110-135, src/cluster_erp/modules/production/scheduling/services.py:389-426).
  • POST /scheduling/production-orders/{order_id}/auto-schedule schedules all pending, unlocked work orders of an order forward in operation order (src/cluster_erp/modules/production/scheduling/routes.py:136-174, src/cluster_erp/modules/production/scheduling/services.py:427-496).
  • POST /scheduling/recompute re-derives the ends of stale scheduled work orders over the current calendar, keeps the starts, and clears the stale marks (src/cluster_erp/modules/production/scheduling/routes.py:175-190, src/cluster_erp/modules/production/scheduling/services.py:605-657).

Why it is built this way¶

Code comments state three reasons. Only pending work orders are schedulable because started or completed ones are pinned by their actuals (src/cluster_erp/modules/production/scheduling/services.py:321-323). The end is derived because a job's length is a function of quantity and routing (src/cluster_erp/modules/production/scheduling/services.py:363-368). The organisation's calendar is owned by its party, so the chain asks for the party (src/cluster_erp/modules/production/scheduling/services.py:77-84). Other rationale is not stated in code or in the project's written engineering rules.

Rules and boundaries¶

  • Writes need work_order.update (src/cluster_erp/modules/production/scheduling/routes.py:91-178).
  • scope=mine without an employee link gives an empty board (src/cluster_erp/modules/production/scheduling/services.py:182-187).
  • A working calendar change marks the affected scheduled work orders stale through WorkingCalendarChanged (src/cluster_erp/modules/production/module.py:1119-1138).

Limits and open points¶

Not determined from code: a limit on the number of work orders the board returns per call; the code reads all work orders that overlap the window (src/cluster_erp/modules/production/scheduling/services.py:1038-1204).
