Device classes

How device-class.js classifies a screen as pc, tablet, or phone, and how that sets the home grid, dock, floating button, and layout key.

The web app gives one answer to the question of what kind of screen it runs on, and every surface reads that answer. webapp/js/device-class.js defines three device classes and the thresholds between them. This page explains the decision, what each class changes, and how a class change is handled while the app runs. The home screen and dock are on home screen, dock, and launcher.

In short¶

  • There are three classes: pc, tablet, and phone (webapp/js/device-class.js:22-26).
  • pc means the pointer can hover and is fine, at any window width. Otherwise a window up to 640 px wide is phone and a wider one is tablet (webapp/js/device-class.js:16-33).
  • The dock mounts only on pc with a window at least 900 px wide (webapp/js/device-class.js:17-19, webapp/js/device-class.js:35-36).
  • Each class has its own home grid and its own saved layout in the user account (webapp/js/device-class.js:22-26).

How it works¶

The decision¶

The flowchart shows how the class and the dock are decided.

In words:

  1. hasFinePointer() tests the media query (hover: hover) and (pointer: fine) (webapp/js/device-class.js:16, webapp/js/device-class.js:28).
  2. If it matches, the class is pc (webapp/js/device-class.js:31).
  3. Otherwise the class is phone when window.innerWidth is at most PHONE_MAX_WIDTH (640), else tablet (webapp/js/device-class.js:20, webapp/js/device-class.js:32).
  4. isPcPointer() adds the width test PC_MIN_WIDTH (900). The dock mounts only when it is true and the page is not a duplicated tile (webapp/js/device-class.js:19, webapp/js/device-class.js:36, webapp/js/app-wheel.js:87-93).

What each class sets¶

Class Board columns by rows Server layout key Local cache key Dock possible Source
pc 8 by 5 springboard cluster_springboard yes, from 900 px webapp/js/device-class.js:23
tablet 6 by 5 springboard_tablet cluster_springboard_tablet no webapp/js/device-class.js:24
phone 4 by 5 springboard_phone cluster_springboard_phone no webapp/js/device-class.js:25

applyBoardProfile(cls) copies the columns, rows, and keys into the home screen and publishes them to CSS as --board-cols, --board-rows, and data-board-class (webapp/js/home.js:65-79).

Other effects of the class:

  • The floating button is hidden only when the user docked it and isPcPointer() is true. On phones, tablets, and narrow PC windows it always stays, so an open app always has a way home (webapp/js/home.js:1040-1047).
  • Compact row density applies only on fine-pointer devices (webapp/js/prefs.js:79-83).
  • On touch, a tile must be held for 450 ms before it can be dragged; a finger that moves earlier scrolls (webapp/js/home.js:77-82, webapp/js/touch-gate.js:1-22).

A class change at run time¶

onDeviceClassChange(cb) listens to resize and to the media query, waits 120 ms for the events to settle, and calls back only when the class really changed (webapp/js/device-class.js:38-64). The home screen then applies the new profile, reconciles, renders, and reads the layout for the new class from the server (webapp/js/home.js:4481-4492).

First use of a class¶

When the server holds no layout for the current class and the browser has no cached one, the home screen starts from the PC layout, reflows it onto the smaller board, and saves it as the class's own layout (webapp/js/home.js:4590-4612). The PC layout itself is never changed by another class (webapp/js/device-class.js:6-14).

Why it is built this way¶

  • The comment in webapp/js/device-class.js:1-4 states that one module answers the question so that no surface can disagree with another.
  • The comment in webapp/js/home.js:52-56 states that an eight-column layout squeezed into a phone was unreadable, so each class has its own arrangement.
  • The comment in webapp/js/home.js:1040-1043 states that the button stays outside a dock so that an open app is never left without a way home.

Rules and boundaries¶

  • The project's written engineering rules state that the PC experience is the launcher, detected by hover, a fine pointer, and at least 900 px, and that the mobile and tablet design is defined separately.

Warning

Discrepancy. The project's written engineering rules tie the PC experience to hover, a fine pointer, and a width of at least 900 px. In code the pc class needs only hover and a fine pointer at any width (webapp/js/device-class.js:6-7, webapp/js/device-class.js:30-33); the 900 px test applies only to mounting the dock (webapp/js/device-class.js:35-36). A narrow PC window therefore gets the 8 by 5 board without a dock. This page documents the code.

  • Browser tests: web-client/_e2e_mobile_home.mjs, web-client/_e2e_mobile_app.mjs, web-client/_e2e_touch_sweep.mjs, web-client/_e2e_app_wheel.mjs.

Interaction with other parts¶

  • The saved layouts are UI-state keys; see user UI state.
  • Drag surfaces in app bundles use the touch gate from the platform context; see gated app bundles.

Limits and open points¶

  • The class uses the window's own width, so a split pane narrower than 640 px on a touch screen is a phone pane. The dock is never mounted inside a pane (webapp/js/app-wheel.js:93).
  • No server setting or user preference overrides the class. A search for other writers of boardClass in webapp/js/ found only applyBoardProfile.
